# v0.2 计划：线上专员产品化、命令收敛与运行可靠性

> 目标：把当前“能跑的 Feishu → Codex remote-control bot”升级成更像产品的 Feishu Agent Remote v0.2。v0.2 不做多 runtime，仍只支持 Codex；重点是架构分层、命令命名统一、运行状态持久化、卡死可恢复、开源用户更容易上手。

## 1. 背景与当前问题

当前项目已经具备核心链路：

- `lark-cli event consume im.message.receive_v1 --as bot` 接收飞书/Lark 消息；
- `RemoteRouter` 将消息路由到命令或当前绑定 Codex session；
- `CodexRunner` 使用 `codex exec` / `codex resume` 执行本机任务；
- SQLite 保存 session binding、remote agents、confirmations；
- `LarkGateway` 使用 `lark-cli im +messages-reply` 和 `+messages-send` 回复/发送消息。

但 v0.1 仍有几个明显的产品化和架构问题：

1. `RemoteRouter` 职责过重：命令解析、权限校验、业务 handler、Codex 调度、回复文案、确认单逻辑都在一个类里。
2. 用户概念不统一：用户理解的是“线上专员”，代码里同时暴露 `remote_agents`、`sessions`、`codex_session_id` 等底层概念。
3. 运行状态只在内存里：`active_runs` 可以避免同一进程内重复执行，但 bot 重启后状态会丢，也无法可靠 `/cancel`。
4. 命令命名仍有 Codex 痕迹：`/remote-codex`、`/recent-codex` 不适合作为长期公开接口。
5. 部分命令语义相近：`/sessions`、`/recent-codex`、`/remote-codex` 容易让用户困惑。
6. 缺少刚需运维命令：`/help`、`/doctor`、`/rename`、`/cancel`、`/runs`、`/pending`。
7. 长任务体验不足：任务开始/运行/完成/失败没有持久记录，也没有可查询的 run history。

## 2. v0.2 产品目标

v0.2 的目标不是扩展更多 Agent runtime，而是把 Codex-only 版本做稳、做清楚。

### 2.1 用户侧目标

用户应该能在飞书里自然完成：

- 创建一个具名线上专员；
- 查看所有线上专员；
- 切换当前聊天绑定到某个线上专员；
- 查看当前专员状态、最近任务和错误；
- 取消卡住的任务；
- 重命名专员；
- 查看 repo 白名单和本机 Codex session；
- 安全地确认外发消息。

### 2.2 工程侧目标

实现层面应达成：

- 命令解析与命令执行分离；
- Agent、Binding、Run、Confirmation 四类状态模型清晰；
- running 状态和 run history 持久化到 SQLite；
- Codex 子进程 pid 可记录、可取消；
- 旧命令保留 alias，避免用户已有习惯立即失效；
- README 命令表和中文文档同步更新；
- 单元测试覆盖命令 alias、run 状态、cancel、rename、help/doctor 等核心路径。

## 3. 核心概念模型

v0.2 统一使用以下概念。

### 3.1 Agent（线上专员）

Agent 是用户主要感知的对象。

建议字段：

- `id`：例如 `rc_ab12cd34`，保持现有格式；
- `title`：用户可读名称，例如 `agent-console`；
- `repo_alias`：当前默认 repo；
- `repo_path`：repo 绝对路径；
- `codex_session_id`：底层 Codex session；
- `status`：`idle | running | failed | removed`，v0.2 可先不做软删除，实际删除仍可物理删除；
- `last_run_id`：最近一次任务；
- `last_error`：最近失败摘要；
- `created_at`、`updated_at`。

### 3.2 Binding（聊天上下文绑定）

Binding 只表达“当前飞书聊天/线程正在操作哪个 Agent”。

建议字段沿用现有 `sessions` 表，但语义重命名为 bindings：

- `chat_id`；
- `thread_key`；
- `agent_id`；
- `updated_at`。

v0.2 可先不强制迁表名，内部代码可以先引入 `BindingStore`/方法名，底层仍用 `sessions` 表以减少迁移风险；但用户命令不再叫 `/sessions`。

### 3.3 Run（一次任务执行）

Run 是 v0.2 最重要的新模型，用来解决卡死、可观测和历史问题。

新增 SQLite 表 `runs`：

- `id`：例如 `run_` + 8 位短 uuid；
- `agent_id`：可空；新建 agent 前的 `/new` 初始运行可以先用临时 key，拿到 session 后补 agent_id；
- `chat_id`；
- `message_id`；
- `repo_alias`；
- `repo_path`；
- `codex_session_id`；
- `prompt`：原始用户任务，建议截断或完整保存 v0.2 二选一；默认完整保存，但不要保存 secrets；
- `status`：`queued | running | succeeded | failed | timed_out | cancelled`；
- `pid`：Codex wrapper 进程 pid；
- `started_at`；
- `finished_at`；
- `summary`：最终回复摘要；
- `error`：失败原因。

### 3.4 Confirmation（待确认操作）

沿用现有 `confirmations`，但新增 `/pending` 展示，必要时支持自然语言“确认”。

v0.2 不扩大高风险操作范围，只保留 `/send` 的 approval-gated 用户身份发送。

## 4. 架构改造计划

### 4.1 分层目标

将当前 `RemoteRouter` 拆成以下层次：

1. `CommandParser`
   - 输入：`IncomingMessage.content` 和 `bot_names`；
   - 输出：结构化 `Command`，例如 `Command(name="new", args=..., raw=...)`；
   - 负责 alias 归一化，如 `/remote-codex` → `/agents`。

2. `CommandRouter`
   - 负责权限校验、选择 handler、统一捕获错误；
   - 不直接实现具体业务细节。

3. `CommandHandlers`
   - 每个命令一个 handler 或一组 handler；
   - 依赖 `StateStore`、`RunManager`、`CodexRunner`、`LarkGateway`。

4. `RunManager`
   - 负责创建 run、记录 pid、更新状态、cancel；
   - 负责同一 agent 的 busy guard；
   - 包装 `CodexRunner.start/resume`。

5. `StateStore`
   - 继续封装 SQLite；
   - 新增 runs 相关方法；
   - 增加 agent rename、last_error、last_run 更新。

6. `main.py`
   - 只保留事件消费、去重、群聊过滤、分发到 router；
   - 不放业务规则。

### 4.2 保持不做的事

v0.2 明确不做：

- 不支持 Claude Code / Gemini / OpenCode 等多 runtime；
- 不做复杂权限模型，例如每个 repo 单独授权；
- 不引入 Web dashboard；
- 不引入外部数据库；
- 不改变当前 `lark-cli` 为主的 Feishu 接入方式。

## 5. 命令体系重命名与合并

### 5.1 新命令表

v0.2 推荐公开命令：

| 命令 | 作用 | v0.2 优先级 |
| --- | --- | --- |
| `/help` | 查看核心命令和当前上下文提示 | P0 |
| `/status` | 查看当前绑定 agent、状态、repo、最近 run、pending confirmations | P0 |
| `/new <repo> <title> [task]` | 创建新的线上专员；task 可省略，省略时待命 | P0 |
| `/agents [n]` | 列出线上专员 | P0 |
| `/attach <agent_id>` | 当前聊天切换到指定线上专员 | P0 |
| `/detach` | 解除当前聊天绑定，不删除 agent | P0 |
| `/remove <agent_id>...` | 删除一个或多个线上专员和相关绑定 | P0 |
| `/rename <agent_id> <title>` | 重命名线上专员 | P0 |
| `/runs [agent_id] [n]` | 查看最近任务记录 | P0 |
| `/cancel [agent_id]` | 取消正在运行的任务，默认当前绑定 agent | P0 |
| `/repos` | 列出 repo 白名单 | P1 |
| `/switch-repo <alias>` | 切换当前 agent 的 repo | P1 |
| `/codex-sessions [n]` | 扫描本机 Codex 历史 session | P1 |
| `/handoff [agent_id]` | 让 agent 生成标准交接总结 | P1 |
| `/pending` | 查看待确认操作 | P1 |
| `/send <open_id> <text>` | 创建 user 身份发送确认单 | P1 |
| `/approve <id>` | 批准确认单 | P1 |
| `/reject <id>` | 拒绝确认单 | P1 |
| `/doctor` | 检查 lark-cli、Codex、配置、repo 路径、state DB | P1 |

### 5.2 旧命令 alias

为了兼容已有用户习惯，v0.2 保留旧命令 alias，但 README 主表只展示新命令。

| 旧命令 | 新命令 | 策略 |
| --- | --- | --- |
| `/remote-codex [n]` | `/agents [n]` | 保留 alias，回复中提示“以后可用 /agents” |
| `/recent-codex [n]` | `/codex-sessions [n]` | 保留 alias |
| `/sessions` | `/bindings` 或隐藏调试命令 | 不推荐公开；README 移除或放 Debug 区 |
| `/close` | `/detach` | 保留 alias |
| `/repo` | `/repos` | 无参数时 alias 到 `/repos` |
| `/repo <alias>` | `/switch-repo <alias>` | 保留 alias，但回复提示新命令 |
| `/summarize` | `/handoff` 或普通自然语言 | 保留 `/summarize` alias 到 `/handoff` |

### 5.3 命令体验细节

- `/help` 根据是否有当前绑定 agent 展示不同提示。
- `/status` 不再把长 `codex_session_id` 放在最前面；优先展示 agent title、agent id、repo、状态、last run。
- `/agents` 用 `*` 标记当前绑定 agent。
- `/runs` 默认展示当前绑定 agent 最近 5 条 run；没有绑定时展示全局最近 10 条。
- `/cancel` 默认取消当前绑定 agent 的 running run；也支持 `/cancel <agent_id>`。
- `/rename` 成功后如果重命名的是当前绑定 agent，回复明确“当前线上专员已重命名”。
- `/pending` 没有待确认时返回“当前没有待确认操作”。
- 如果用户回复“确认”，且当前 sender 在当前 chat 下只有一个 pending confirmation，则等价于 `/approve <id>`；如果有多个 pending，则提示用 `/pending` 和 `/approve <id>`。

## 6. 新增刚需命令设计

### 6.1 `/help`

目的：开源用户第一次启动后能知道怎么用。

返回内容：

- 当前是否有绑定 agent；
- 最常用命令 6-8 个；
- 一条创建示例；
- 一条排障提示，例如 `/doctor`。

### 6.2 `/rename <agent_id> <title>`

目的：修正 `/new` 创建时 title 不理想的问题。

行为：

- agent 不存在：回复未找到；
- title 为空：回复用法；
- title 建议限制长度，例如 60 字符；
- 更新 `remote_agents.title` 和 `updated_at`。

### 6.3 `/cancel [agent_id]`

目的：解决 Codex 子进程卡住导致体验变差的问题。

行为：

- 不传 agent_id：使用当前绑定 agent；
- agent 没有 running run：回复“当前没有运行中的任务”；
- 有 running run 且有 pid：先 `terminate`，短等待后 `kill`；
- 更新 run status 为 `cancelled`，写入 `finished_at` 和 summary；
- 给用户回复被取消的 run id。

### 6.4 `/runs [agent_id] [n]`

目的：让用户查看最近任务，尤其是长任务和失败任务。

行为：

- 有 agent_id：列该 agent 最近 n 条；
- 无 agent_id 且当前聊天已绑定：列当前 agent 最近 5 条；
- 无 agent_id 且未绑定：列全局最近 10 条；
- 每行展示：run id、agent title/id、status、耗时、摘要前 60 字。

### 6.5 `/doctor`

目的：提升开源可用性和排障效率。

检查项：

- `lark-cli` 是否可执行；
- `lark-cli event list` 是否可用；
- `codex` 是否可执行；
- config 文件是否存在且可解析；
- `owner_open_id` 和 `authorized_open_ids` 是否存在；
- repo alias 路径是否存在；
- state sqlite 是否可打开；
- 当前进程是否能写 log/state。

v0.2 中 `/doctor` 可以只做本地同步检查，不需要发起真实飞书消息。

### 6.6 `/handoff [agent_id]`

目的：产品化“总结进展”，替代偏底层的 `/summarize`。

行为：

- 默认当前绑定 agent；
- 指定 agent_id 时总结该 agent；
- prompt 固定为中文/英文都可接受的结构化交接模板：目标、已完成、关键修改、验证、风险、下一步；
- 内部仍调用 `codex resume`，所以它不是只读 inspection；README 需要说明。

## 7. RunManager 与卡死恢复设计

### 7.1 Run 生命周期

状态流转：

```text
queued -> running -> succeeded
queued -> running -> failed
queued -> running -> timed_out
queued -> running -> cancelled
```

v0.2 可以不实现复杂 queue；创建后几乎立即从 `queued` 进入 `running`。保留 `queued` 是为了以后扩展。

### 7.2 同一 agent busy guard

规则：

- 同一 agent 同时只能有一个 running run；
- 如果用户继续对 running agent 发普通文本，立即回复“当前线上专员还在处理上一条任务”；
- `/status`、`/agents`、`/runs`、`/cancel` 不受 busy guard 阻塞；
- 新建 `/new` 可以并行，因为新 agent 尚未绑定到同一 agent。

### 7.3 Codex pid 记录

`CodexRunner` 需要在子进程启动后把 pid 交给 `RunManager`。

可选实现方式：

- `CodexRunner.start/resume` 接受 `on_started(pid)` callback；
- 或返回一个 `RunningProcess` 对象，由 `RunManager` await。

推荐 v0.2 使用 callback，改动小：

```python
await codex_runner.resume(session_id, repo_path, prompt, on_started=lambda pid: state.mark_run_running(run_id, pid))
```

### 7.4 Timeout 行为

沿用现有 `timeout_seconds=1800`，但 timeout 后必须：

- 终止子进程；
- run status 写成 `timed_out`；
- agent status 回到 `idle` 或 `failed`；
- 用户收到“执行超时，已终止”的回复；
- `/runs` 能看到这次 timeout。

## 8. 数据库迁移计划

v0.2 保持轻量迁移：启动时 `_init_db()` 自动 `CREATE TABLE IF NOT EXISTS` 和 `_ensure_column()`。

新增内容：

1. `runs` 表；
2. `remote_agents.last_run_id` 列；
3. `remote_agents.last_error` 列；
4. 可选：`remote_agents.status` 继续沿用现有列；
5. 可选：暂不改 `sessions` 表名，避免破坏已有 state。

迁移要求：

- 已有 state.sqlite 能无损升级；
- 没有 runs 表时自动创建；
- 没有 last_run_id/last_error 时自动加列；
- 旧 agent 仍能被 `/agents`、`/attach`、`/status` 识别。

## 9. 回复文案设计

### 9.1 `/status` 推荐格式

```text
当前线上专员：agent-console
Agent ID：rc_ab12cd34
Repo：agent
状态：running
最近任务：run_1234abcd running 2m13s
待确认：无

可用：/runs /cancel /detach /help
```

如果未绑定：

```text
当前聊天未绑定线上专员。
可用 /agents 查看，或 /new <repo> <title> 创建。
```

### 9.2 `/agents` 推荐格式

```text
线上专员：
* rc_ab12cd34 `agent-console` repo=agent status=running last_run=run_1234abcd
- rc_ef56gh78 `bug-hunter` repo=app status=idle updated=2026-05-15 12:00:00
```

### 9.3 `/runs` 推荐格式

```text
最近任务：
- run_1234abcd running 2m13s `检查发版风险`
- run_5678efgh succeeded 41s `总结当前 repo 进展`
- run_9999zzzz cancelled 5m02s `我授权了，你再试试`
```

## 10. 测试计划

### 10.1 单元测试

新增或更新测试覆盖：

- `/agents` 与 `/remote-codex` alias 行为一致；
- `/codex-sessions` 与 `/recent-codex` alias 行为一致；
- `/detach` 与 `/close` alias 行为一致；
- `/repos` 与 `/repo` 无参数 alias 行为一致；
- `/switch-repo <alias>` 与 `/repo <alias>` alias 行为一致；
- `/rename` 成功、agent 不存在、title 缺失；
- `/runs` 在有/无绑定时的默认列表；
- `/cancel` 成功、无 running run、未绑定且未传 agent_id；
- run 表创建、run 状态流转、pid 写入；
- Codex timeout 写入 `timed_out`；
- busy guard 不阻塞 `/status`、`/runs`、`/cancel`；
- `/pending` 展示 pending confirmations；
- “确认”在单个 pending 时自动 approve，在多个 pending 时要求明确 id；
- `/help` 在有绑定/无绑定时返回合理内容；
- `/doctor` 在 fake 环境下返回检查结果。

### 10.2 手工验证

本机飞书真实验证：

1. `/doctor`，确认 lark-cli、codex、config、repo、state 均通过；
2. `/new agent agent-console` 创建待命专员；
3. `/agents` 查看并确认 `*` 标记；
4. 普通文本触发一次 Codex run；
5. run 过程中发 `/status`，确认能立即回复 running；
6. run 过程中发 `/runs`，确认看到 running run；
7. run 过程中发 `/cancel`，确认子进程终止且 run 变 `cancelled`；
8. `/rename <agent_id> new-title`，确认 `/status` 和 `/agents` 更新；
9. `/detach` 后 `/status` 显示未绑定；
10. `/attach <agent_id>` 重新绑定；
11. `/send <open_id> test` → `/pending` → `/approve <id>`，确认 approval flow；
12. 旧命令 `/remote-codex`、`/recent-codex`、`/close` 仍可用。

## 11. 实施顺序建议

### Phase 1：命令 parser 与 alias 收敛

- 引入 `CommandParser`；
- 实现新命令名和旧 alias；
- README/中文 README 主命令表改成新命令；
- 先不改变状态结构。

### Phase 2：StateStore 增加 runs 和 agent 更新能力

- 新增 runs 表；
- 增加 run CRUD 方法；
- 增加 agent rename、last_run、last_error 方法；
- 保持现有测试全绿。

### Phase 3：RunManager 接管 Codex 执行

- 将 `_new_session`、`_continue_session`、`_handoff` 的 Codex 调用移入 RunManager；
- 记录 pid、status、summary、error；
- 实现 busy guard 和 `/cancel`。

### Phase 4：新增刚需命令

- `/help`；
- `/rename`；
- `/runs`；
- `/pending`；
- `/doctor`；
- `/handoff`，并保留 `/summarize` alias。

### Phase 5：真实飞书回归与文档更新

- 按手工验证清单跑一遍；
- 更新 README、README.zh-CN.md、config.example.yaml；
- 若有 launchd 行为变化，同步说明。

## 12. 成功标准

v0.2 完成时应满足：

- 用户主要命令不再暴露 `remote-codex` / `recent-codex` 这样的旧命名；
- 旧命令仍能作为 alias 工作；
- Codex 卡住时可以 `/status`、`/runs`、`/cancel`；
- run history 在 bot 重启后仍可查询；
- 线上专员可以重命名、删除、解绑、重新 attach；
- README 和中文 README 的命令表一致；
- 单元测试覆盖新增命令和迁移；
- 真实飞书私聊中完成一次 create → run → cancel/status → rename → attach/detach 流程。

## 13. 暂缓项

以下内容有价值，但不放入 v0.2：

- 多 runtime 抽象和 Claude Code / Gemini / OpenCode 支持；
