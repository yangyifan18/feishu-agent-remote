# v0.5 Goal Plan：可用性与安全修复（P0/P1）

> Goal：把 Feishu Agent Remote 从“已能长期运行”推进到“关键故障模式可控”。本版只修实际影响可用性和安全性的 P0/P1 问题：事件去重、事件消费者退避、`/new` 并发、异步取消、SQLite 迁移 SQL 硬化。P3 的流式卡片和多 workspace 仅记录后续架构方向，不在本目标内实现。

## 1. Goal Definition

### 1.1 目标结果

完成后应满足：

1. 重复事件不会因为 dedupe 缓存满 10k 后全量清空而被重新处理。
2. `lark-cli event consume` 在坏配置/认证失败/快速崩溃时不会每 5 秒无限热循环，而是指数退避。
3. 同一飞书 chat/thread 内两个并发 `/new` 不会启动两个 runtime 并创建重复线上专员。
4. `/cancel` 不会因为同步 `time.sleep(0.2)` 阻塞整个 asyncio event loop。
5. SQLite additive migration 不再使用可扩散的 f-string SQL identifier 拼接模式。
6. 现有 v0.4 功能不回归：launchd service、canonical config/state、templates、multi-runtime、repo allowlist、approval-gated `/send` 都保持可用。

### 1.2 非目标

本目标明确不做：

- 不实现飞书流式卡片回复。
- 不实现多 workspace / 多 Feishu app。
- 不做 SQLite 主键重构或 workspace 维度迁移。
- 不引入新的 runtime。
- 不改变公开命令语义，除非是错误提示更明确。
- 不把 event dedupe 持久化到 SQLite；本版仍使用进程内缓存。

### 1.3 成功判定

本目标完成的判定标准：

- 单元测试覆盖新增故障模式，并全部通过。
- `py_compile` 和 `git diff --check` 通过。
- 本机 `python -m remote_control.cli service restart` 后服务正常运行。
- 飞书真实 smoke 通过：`/doctor`、`/new template=reporter agent v05-smoke 只回复 v0.5 smoke ok，不要修改文件`、`/status`。

## 2. Work Items

### G1 — 事件去重缓存不再全量清空

当前问题：`main.py` 使用全局 `_processed: set[str]`，超过 10000 后 `clear()`。一旦清空，近期已经处理过的重复事件可能再次执行。

实现要求：

- 新增 `ProcessedEventCache`，建议放在 `main.py` 或独立小模块；优先保持改动局部。
- 内部使用 `collections.OrderedDict[str, float]`。
- 默认参数：`max_size=10000`、`ttl_seconds=86400`。
- 提供 `seen_or_add(key: str, now: float | None = None) -> bool`：
  - key 已存在且未过期：返回 `True`，并刷新/移动到最近位置。
  - key 不存在或已过期：加入缓存，返回 `False`。
  - 每次新增时先清理过期 key，再逐个淘汰最旧 key，直到 size <= max_size。
- `handle_event` 使用 `processed_events.seen_or_add(dedup_key)` 代替 `_processed` set。
- `dedup_key` 本版仍为 `event.get("event_id") or incoming.message_id`。

验收测试：

- 填充超过 `max_size` 后，最近加入的 key 仍能 dedupe，最旧 key 被淘汰。
- TTL 过期后同 key 可再次加入。
- 同一 event 调两次 `handle_event`，router 只收到一次。

### G2 — lark-cli event consumer 指数退避

当前问题：`consume_events_forever` 在 consumer 退出后固定 5 秒重启。坏配置、权限失效或 CLI 快速崩溃时会热循环。

实现要求：

- 引入 `EventConsumerBackoff` 或等价小对象：
  - `initial_delay=5.0`
  - `max_delay=60.0`
  - `stable_after=60.0`
  - 连续快速失败：5、10、20、40、60、60...
  - 单次运行时长 >= 60 秒：下一次 delay 重置为 5。
- `consume_events_forever` 记录每轮启动时间和退出时间。
- consumer 退出后记录 return code 和下一次 restart delay。
- 保持现有 stderr logging 与 graceful terminate/kill 逻辑。
- 为测试可注入 sleeper/clock/process factory；不要为了测试真实启动 lark-cli。

验收测试：

- fake consumer 立即退出时，sleep delay 递增并封顶。
- fake consumer 稳定运行超过 `stable_after` 后，下一次 delay 回到 5。
- 非 JSON 行仍被忽略，已有事件处理逻辑不回归。

### G3 — `/new` 和 agentless run 绑定级并发锁

当前问题：`RunManager.resume_agent` 有 per-agent lock，但 `start_new` 没有锁。同一 chat/thread 并发 `/new` 可能创建重复 runtime run 和重复线上专员。

实现要求：

- `RunManager` 新增 `_binding_locks: dict[str, asyncio.Lock]`。
- 新增 `_lock_for_binding(chat_id: str, thread_key: str) -> asyncio.Lock`，lock key 可为 `f"{chat_id}:{thread_key}"`。
- `start_new` 新增必填 `thread_key: str` 参数。
- `CommandHandlers._new_session` 调用 `start_new(..., thread_key=_binding_key(msg))`。
- `start_new` 在 binding lock 内检查是否存在该 chat/thread 的 queued/running run。
  - 推荐新增 `StateStore.get_running_run_for_binding(chat_id, thread_key)`。
  - 因当前 `runs` 表没有 `thread_key`，本版可添加 additive 列：`thread_key TEXT`。
  - `create_run` 接受 `thread_key: str | None = None` 并保存。
- 如果存在 running/queued run，抛 `RunAlreadyActive(existing)`。
- `_new_session` 捕获 `RunAlreadyActive`，回复：`当前聊天正在创建线上专员或处理任务：<run_id>。可稍后再试，或 /runs 查看。`
- `resume_session(agent_id=None, ...)` 可选支持 `thread_key`；有 `thread_key` 时使用同一 binding lock 和 running check，无 key 时保持当前行为。

验收测试：

- 同一 chat/thread 两个并发 `/new`：只调用一次 runner.start，只创建一个 remote agent，另一条收到 busy 回复。
- 不同 chat 或不同 thread 的并发 `/new`：都可以执行。
- 旧数据库迁移后 `runs.thread_key` 自动补列，旧 run 可正常读取。

### G4 — 取消任务不阻塞 event loop

当前问题：`terminate_process_group` 是同步函数，内部 `time.sleep(0.2)`；从 async handler 调用时会阻塞事件循环。

实现要求：

- `terminate_process_group(pid: int)` 改为 `async def terminate_process_group(pid: int, grace_seconds: float = 0.2) -> None`。
- `time.sleep(0.2)` 改为 `await asyncio.sleep(grace_seconds)`。
- `RunManager.cancel_agent` 改为 async，并 `await terminate_process_group(...)`。
- `CommandHandlers._cancel` 改为 `run = await self.run_manager.cancel_agent(agent_id)`。
- 保持信号语义不变：先 `SIGTERM` process group，再 grace，再 `SIGKILL`；`ProcessLookupError` 忽略；`PermissionError` fallback 到 `os.kill(pid, SIGTERM)`。

验收测试：

- 取消流程仍将 run 标记为 `cancelled`，agent status 回到 `idle`。
- 用 fake terminate 或 monkeypatch sleep，证明 `_cancel` await 路径正常。
- 并发 heartbeat coroutine 在 cancel grace 期间可继续推进，证明不再阻塞 event loop。

### G5 — SQLite migration SQL 硬化

当前问题：`StateStore._ensure_column` 用 f-string 拼 `PRAGMA table_info({table})` 和 `ALTER TABLE {table} ADD COLUMN {column} {spec}`。当前调用值不是用户输入，但模式不安全。

实现要求：

- 将 `_ensure_column(conn, table, column, spec)` 改为 `_ensure_column(conn, table, column)`。
- 定义固定白名单 `_COLUMN_MIGRATIONS: dict[tuple[str, str], str]`，包含当前所有 additive 列：
  - `sessions.agent_id`
  - `sessions.runtime`
  - `sessions.runtime_session_id`
  - `remote_agents.last_run_id`
  - `remote_agents.last_error`
  - `remote_agents.runtime`
  - `remote_agents.runtime_session_id`
  - `runs.runtime`
  - `runs.runtime_session_id`
  - `runs.thread_key`（若 G3 加列）
- `_column_exists` 使用：`SELECT 1 FROM pragma_table_info(?) WHERE name = ?`。
- 未知 `(table, column)` 直接 `raise ValueError`。
- `delete_remote_agents` 的动态 placeholder 方案可保留；它只拼接由长度生成的 `?`，值仍通过参数绑定。
- `list_confirmations` 的动态 where 拼接可保留；只允许固定 SQL 片段，值仍通过参数绑定。

验收测试：

- legacy schema 缺列时，`StateStore` 初始化后自动补列，旧数据保留。
- 未知 migration key 抛 `ValueError`。
- 恶意 agent_id 传给 `delete_remote_agents` 不删除其他 agent。
- 恶意 requester_id/chat_id 传给 `list_confirmations` 不泄露其他 confirmation。

## 6. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| `runs.thread_key` additive migration 影响旧 DB | 只 add column，不改主键；旧 row 的 `thread_key` 可为空，读取逻辑兼容。 |
| binding lock 误拦截不同线程 | `_binding_key(msg)` 继续作为唯一来源；补不同 thread 并发测试。 |
| backoff 测试误启动真实 lark-cli | 通过 process factory/sleeper/clock 注入，测试不跑真实 CLI。 |
| async cancel 改签名导致 handler 漏 await | 修改 `_cancel` 并跑 cancel 相关测试；py_compile 可捕获部分错误。 |
| SQL hardening DDL 白名单漏项 | 单测覆盖已有 legacy migration；启动真实 state 做 `/doctor` smoke。 |
