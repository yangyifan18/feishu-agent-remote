# v0.6 P3 Design：流式卡片回复与多 Workspace

> 目标：为 Feishu Agent Remote 的差异化能力做一份可执行的架构计划。v0.6 关注两个 P3 方向：飞书流式/进度卡片回复，以及多 workspace / 多 Feishu app 支持。本文档是设计文档，不要求在 v0.5 可用性修复中实现。

配套执行计划见：`docs/v0.6-p3-goal-plan.md`。本文保留架构设计与决策背景，执行时以 goal plan 的任务拆分、测试矩阵和 smoke checklist 为准。

## 1. 背景

当前系统已经具备：

- 单个 `lark-cli event consume im.message.receive_v1 --as bot` 长连接；
- 单个 `RemoteConfig`、`StateStore`、`LarkGateway`、`RemoteRouter`；
- Codex / Claude 多 runtime；
- 线上专员、session binding、run history、approval-gated `/send`；
- launchd 常驻和 canonical config/state。

但它仍然是“单 workspace + 文本回复 + 最终结果”的架构：

- `LarkGateway.reply()` 只发 `--text`；
- `CodexRunner` / `ClaudeRunner` 都用 `communicate()` 等进程结束后解析最终消息；
- `RunManager` 只知道 run 的开始/结束状态，不向 UI 层发增量进度；
- `sessions` 的主键是 `(chat_id, thread_key)`，没有 workspace 维度；
- `main.py` 中全局初始化一套 config/router/gateway/state，不能管理多个飞书 app 或 workspace。

## 2. Design Goals

### 2.1 用户体验目标

1. 长任务开始后，用户能看到一个持续更新的进度卡片，而不是多条零散文本消息。
2. 卡片能展示：agent title、repo、runtime、run status、最近输出摘要、开始时间、最终结果。
3. 卡片失败时自动 fallback 到文本回复，不能影响任务执行。
4. 同一个本地服务可以监听多个飞书 workspace / bot app，每个 workspace 独立授权、独立 repo 白名单、独立聊天绑定。

### 2.2 工程目标

1. P3 功能必须 opt-in，不能破坏现有 P0 文本路径。
2. Cards 是 presentation layer，不应该污染 command handlers 和 runtime runners。
3. Multi-workspace 是 scoped runtime/container，不应该重写所有命令逻辑。
4. 当前单 workspace 配置必须保持兼容，并自动映射到 workspace `default`。
5. 所有状态、确认单、dedupe 都必须能按 workspace 隔离。

## 3. Non-goals

v0.6 不应该一次性做完所有事情：

- 不要求第一版卡片支持真正 token-level streaming；可以先支持 run lifecycle updates。
- 不要求替换现有文本回复；text path 永远作为 fallback。
- 不要求一次性迁移 SQLite 主键；可以通过兼容层或新表逐步推进。
- 不要求多 workspace 共享 agent/session；默认隔离。
- 不要求把 secrets 写入 config；多个 workspace 的敏感信息继续交给 lark-cli profile / 本地 env 管理。

## 4. Architecture Overview

建议引入三个核心 seam：

1. `ReplyGateway`：抽象文本回复、卡片创建、卡片更新、用户身份发送。
2. `ProgressReporter`：把 run lifecycle / runtime events 转成 reply updates。
3. `WorkspaceManager`：管理多个 workspace 下的 router/gateway/state/config。

简化数据流：

```text
lark-cli event consumer(s)
        ↓
WorkspaceManager resolves workspace_id
        ↓
RemoteRouter(workspace-scoped config/state/gateway)
        ↓
CommandHandlers
        ↓
RunManager emits RunProgress
        ↓
ProgressReporter
        ↓
ReplyGateway text/card update
```

## 5. Streaming / Progress Card Design

### 5.1 Data Models

建议新增独立模型，避免复用 `RunRecord` 作为 UI 模型：

```python
@dataclass(frozen=True)
class MessageRef:
    workspace_id: str
    chat_id: str
    message_id: str
    thread_key: str

@dataclass(frozen=True)
class ReplyHandle:
    mode: str  # "text" | "card"
    workspace_id: str
    message_id: str
    card_id: str | None = None

@dataclass(frozen=True)
class RunProgress:
    run_id: str
    agent_id: str | None
    title: str
    repo_alias: str
    runtime: str
    status: str  # queued | running | assistant | succeeded | failed | timed_out | cancelled
    text: str
    updated_at: str
```

### 5.2 ReplyGateway Interface

现有 `LarkGateway` 可以逐步扩展为实现该接口：

```python
class ReplyGateway(Protocol):
    async def reply_text(self, ref: MessageRef, text: str) -> ReplyHandle: ...
    async def create_progress_card(self, ref: MessageRef, progress: RunProgress) -> ReplyHandle: ...
    async def update_progress_card(self, handle: ReplyHandle, progress: RunProgress) -> None: ...
    async def send_user_message(self, user_id: str, text: str) -> None: ...
```

兼容要求：

- `LarkGateway.reply(message_id, text)` 暂时保留，内部可转调 `reply_text`。
- 如果当前 `lark-cli` 没有高级 card shortcut，可先通过 `lark-cli api ...` 封装在 gateway 内部，不能泄露到 handlers。
- card API 调用失败时，`ProgressReporter` 应记录错误并 fallback 到 `reply_text`。

### 5.3 ProgressReporter Interface

```python
class ProgressReporter(Protocol):
    async def started(self, run: RunRecord) -> None: ...
    async def update(self, progress: RunProgress) -> None: ...
    async def finished(self, run: RunRecord, result: RuntimeRunResult) -> None: ...
```

实现两个 reporter：

- `TextProgressReporter`：保持现有体验，开始时一条文本，结束时一条文本。
- `CardProgressReporter`：开始时创建卡片，运行中更新卡片，结束时 final update。

### 5.4 Update Policy

卡片更新不能太频繁，否则会触发飞书限流或造成噪音：

- status change：立即更新。
- assistant/progress text：最多每 3-5 秒更新一次。
- final result：必须更新，不受 debounce 影响。
- cancelled/timed_out/failed：必须更新，并保留错误摘要。

### 5.5 Runtime Streaming Roadmap

当前 runners 使用 `communicate()`，可以分两步改：

1. Lifecycle-only progress：不解析 stdout 增量，只在 queued/running/final 更新卡片。
2. Runtime event streaming：
   - Codex：逐行读取 JSONL，解析 assistant message / tool events / final result。
   - Claude：逐行读取 stream-json，解析 assistant/result events。

Runner 签名保持兼容：

```python
async def start(repo_path, prompt, on_started=None, on_event=None) -> RuntimeRunResult: ...
async def resume(session_id, repo_path, prompt, on_started=None, on_event=None) -> RuntimeRunResult: ...
```

`on_event` 为可选参数，旧 fake runner 和旧调用路径无需立即改动。

### 5.6 State Storage

第一版可以把 card handle 存在内存，因为进程重启后重新更新旧卡片不是 P0。

更稳定版本建议新增表：

```text
run_replies(
  run_id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL DEFAULT 'default',
  mode TEXT NOT NULL,
  message_id TEXT,
  card_id TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
)
```

该表不影响现有 `runs`，也方便 card 失败时 fallback 到 text。

## 6. Multi-workspace Design

### 6.1 Config Model

保持旧 config 兼容。新 config 形态建议：

```yaml
default_workspace: personal

shared_repos:
  agent: /Users/you/Code/feishu-agent-remote

shared_runtimes:
  codex:
    type: codex
    bin: codex
    profile: fastrelay

workspaces:
  personal:
    display_name: Personal Feishu
    owner_open_id: ou_xxx
    authorized_open_ids: [ou_xxx]
    bot_names: [your-bot-name]
    repos:
      agent: /Users/you/Code/feishu-agent-remote
    lark_cli_bin: lark-cli
    lark_cli_args: [--profile, personal]
    features:
      card_replies: false

  team:
    display_name: Team Workspace
    owner_open_id: ou_yyy
    authorized_open_ids: [ou_yyy]
    bot_names: [team-codex]
    lark_cli_bin: lark-cli
    lark_cli_args: [--profile, team]
    features:
      card_replies: true
```

旧版单 workspace config 自动变成：

```yaml
default_workspace: default
workspaces:
  default:
    # values copied from old root-level config
```

### 6.2 Runtime Containers

```python
@dataclass(frozen=True)
class WorkspaceConfig:
    id: str
    display_name: str
    owner_open_id: str
    authorized_open_ids: frozenset[str]
    bot_names: tuple[str, ...]
    repos: dict[str, RepoConfig]
    lark_cli_bin: str
    lark_cli_args: tuple[str, ...]
    features: WorkspaceFeatures

@dataclass
class WorkspaceRuntime:
    config: RemoteConfig
    state: StateStore
    gateway: LarkGateway
    router: RemoteRouter

class WorkspaceManager:
    def runtime_for(self, workspace_id: str) -> WorkspaceRuntime: ...
    async def handle_event(self, workspace_id: str, event: dict) -> None: ...
```

关键原则：复用现有 `RemoteRouter` / `CommandHandlers`。多 workspace 只是在外层创建多套 scoped config/gateway/state，不重写命令。

### 6.3 Event Consumers

第一版多 workspace 可以一个 workspace 一个 `lark-cli event consume` 子进程：

```text
consumer personal → WorkspaceManager.handle_event("personal", event)
consumer team     → WorkspaceManager.handle_event("team", event)
```

优点：

- 不依赖事件 payload 中是否带 tenant/app 信息。
- 每个 workspace 可以使用不同 `lark-cli --profile` 或 env。
- 某个 workspace consumer 崩溃时，不影响其他 workspace。

要求：

- 每个 consumer 有独立 backoff。
- stderr log 带 workspace_id prefix。
- dedupe key 改为 `(workspace_id, event_id or message_id)`。

### 6.4 State Scope

最终状态必须隔离：

- `sessions`: `(workspace_id, chat_id, thread_key)`
- `remote_agents`: `workspace_id + id`
- `runs`: `workspace_id`
- `confirmations`: `workspace_id`
- `run_replies`: `workspace_id`

SQLite 迁移建议分阶段：

1. Additive columns：给所有表加 `workspace_id TEXT DEFAULT 'default'`。
2. 代码查询都带 `workspace_id` 过滤。
3. 对新表或 v2 表使用新的唯一约束；不要强行在线修改旧 primary key。
4. 后续版本再考虑 `sessions_v2` 迁移。

### 6.5 Auth and Safety

- `authorized_open_ids` 按 workspace 生效，不能跨 workspace 复用。
- `owner_open_id` 按 workspace 生效。
- repo allowlist 可继承 shared，但 workspace override 必须显式。
- `/send` confirmation 必须包含 workspace_id；审批只能在原 workspace/chat/requester 下完成。
- 多 workspace 不允许默认共享 session/agent。

## 7. Implementation Phases

### Phase 0 — P0/P1 修复（v0.5）

先完成可用性修复：dedupe LRU/TTL、consumer backoff、binding lock、async cancel、SQL hardening。

### Phase 1 — Progress Interface（text-only）

- 添加 `RunProgress` / `ProgressReporter`。
- `RunManager` 在 queued/running/final 发 progress event。
- 默认 reporter 仍然文本回复。
- 不接入飞书 card API。

### Phase 2 — Optional Cards

- 增加 `features.card_replies: false`。
- 实现 `CardProgressReporter` 和 gateway card methods。
- card 失败 fallback text。
- 卡片只做 lifecycle updates，不做 token streaming。

### Phase 3 — Runtime Stdout Streaming

- Codex / Claude runner 改为逐行读取 stdout。
- `on_event` 发 assistant text / tool events / final result。
- 保持现有 final summary 兼容。
- 加 debounce，避免过多 card updates。

### Phase 4 — Workspace Config Compatibility

- 新增 `workspaces:` config loader。
- 旧 config 自动映射为 `default` workspace。
- `WorkspaceManager` 创建 per-workspace runtime。
- 默认仍只启动 `default`。

### Phase 5 — Multiple Event Consumers

- 一个 workspace 一个 event consumer。
- 每个 consumer 独立 backoff、logs、dedupe scope。
- 完成 workspace-scoped state 查询。

## 8. Test Strategy

### 8.1 Cards

- fake gateway 记录 `create_progress_card` / `update_progress_card` 调用。
- card create 失败时 fallback 到 text，run 仍成功。
- debounce suppress 中间 update，但 final update 必发。
- cancelled run 不被迟到的 runtime event 覆盖。

### 8.2 Runtime Streaming

- fake runner 发送 started / assistant / final events。
- Codex JSONL parser 保持现有 session/final message 行为。
- Claude stream-json parser 保持现有 assistant/result 行为。
- timeout/cancel 与 streaming 同时发生时状态正确。

### 8.3 Multi-workspace

- 同一 `chat_id/thread_key` 在两个 workspace 下绑定不同 agent。
- sender 在 workspace A 授权、workspace B 未授权时，B 拒绝。
- workspace-specific bot_names 只影响本 workspace 群聊 mention 过滤。
- confirmation 不能跨 workspace approve。
- dedupe 不会因为 workspace A 的 event_id 命中而丢掉 workspace B 的同 id event。

### 8.4 Integration without Real Feishu

- 构造 fake `lark-cli`，输出 NDJSON event 并捕获 reply/card 参数。
- 启动两个 fake consumers，验证 workspace routing。
- 模拟一个 consumer 快速失败，另一个持续运行，验证隔离。

### 8.5 Manual Smoke

保留现有 smoke：

```text
/doctor
/runtimes
/status
/new template=reporter agent smoke 只回复 smoke ok，不要修改文件
/runs 5
```

Card smoke：

```text
/new template=implementer agent card-smoke 只回复 card smoke ok，不要修改文件
```

验收：看到一张 running card，最终更新为 succeeded；关闭 `card_replies` 后回到 text path。

Workspace smoke：

- personal workspace `/doctor`。
- team workspace `/doctor`。
- 两边同名 repo alias 不串状态。

## 9. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| 飞书 card API / lark-cli 支持不稳定 | 卡片功能阻塞 | card API 全部封装在 gateway；默认关闭；失败 fallback text。 |
| runtime streaming 解析复杂 | 可能影响最终回复 | 保留 final-result parser；streaming event 只做 UI 增量。 |
| workspace state 迁移复杂 | 可能破坏旧用户 DB | 先 additive column，再 scoped query；必要时引入 v2 表，不强改旧 primary key。 |
| 多 consumer 难排障 | 运维复杂 | logs/backoff 全部带 workspace_id；`/doctor` 增加 workspace view。 |
| 权限串 workspace | 安全风险 | auth、confirmations、repo allowlist 全部 workspace-scoped。 |

## 10. Recommended Defaults

- `features.card_replies: false`
- `card_update_min_interval_seconds: 5`
- `workspace_id: default` for old config
- `shared_repos` disabled unless explicitly configured
- `workspace state isolation` required before multiple consumers are enabled

## 11. Open Questions for Later

这些问题不阻塞 v0.5，但实现 v0.6 前需要确认：

1. 飞书 card update 最稳的 API 入口是 `lark-cli api` 还是后续等待官方 CLI shortcut？
2. 多 workspace 是一个 launchd service 管多个 consumers，还是每个 workspace 一个 service？当前推荐前者。
3. 是否允许 workspace 共享同一 repo alias？当前推荐允许 shared read，但 workspace override 显式优先。
4. streaming 是否需要显示 tool call / file edit 摘要，还是只显示 assistant text？当前推荐第一版只显示 assistant text 和 status。
